# Experimental SH3 to x86-64 block compiler

This branch starts at Y, `fe8ab8f029f180a224112d8945b7377fd54ef0e3`.
The rasterizer is unchanged. `FBNEO_SH3_X64_JIT` defaults to **0**: this is
an opt-in research backend, not a demonstrated PS4 performance improvement.

The compiler emits SysV AMD64 instructions into a 4 MiB W^X code arena.
Six guest registers can remain in host registers within a block. It handles
integer ALU/flags/shifts and guarded ordinary mapped byte/word/long reads,
including PC-relative, indexed, displaced and postincrement forms. It does
not emit calls to the interpreter handlers in place of native operations.
The second stage also handles guarded ordinary mapped stores and BT/BF/BTS/BFS.
A taken delayed conditional can execute a pure GPR/SR delay slot natively.
The interpreter handles other branches, non-ALU delay slots, devices,
unsupported operations, pending interrupts and the per-instruction timer mode. Native
blocks execute only in the existing slice-timer mode and within its budget.

The implementation uses Salvia's separation of code validation, native
execution and interpreter fallback as a design reference (source snapshot
`c4e92f3380ac85ef1ee09897806806790ace8b9a`). Its PPC emitter/ABI is not copied
into the PS4 backend. This is not a complete port of the Salvia DRC.

## Correctness boundaries

- Every native entry validates its fetch mapping and instruction snapshot.
  DMA/cheat writes, state restoration and code aliases cannot silently reuse
  changed native code. Negative cache entries run the live interpreter; a
  newly compilable sequence can stay interpreted until eviction.
- Read mappings are looked up at execution time. Internal/device addresses,
  handler mappings and unaligned reads leave the block before that instruction.
  Already completed instructions commit their registers, PC and cycles.
- Write mappings are looked up at execution time too. Before any write or
  predecrement, the actual host destination is checked against this native
  region's source span. Possible overlaps leave the block before the store,
  including aliases through different physical pages. The live interpreter
  executes that store; subsequent native entry validates again.
- Untaken conditional branches continue within a region. Taken branches return
  through the validating dispatcher with exact PC/PPC/EA, delay and extra-cycle
  accounting. Pure arithmetic delay slots can be fused; other slots execute
  once in the interpreter, then permit native entry at the branch target.
  There are no unchecked direct links between generated blocks.
- No cache metadata or generated bytes enter a save state. `Sh3Exit` releases
  both allocations. Allocation or protection failures disable native execution
  for that lifecycle and return to the existing interpreter.
- The emitter preserves its callee-saved scratch registers. It assumes the
  SysV x86-64 ABI and the current disabled `WaitState` implementation. Windows
  and big-endian builds are rejected when the experimental flag is enabled.
- `DT` remains interpreted: its existing busy-loop helper performs a read and
  can consume extra cycles. It must not be treated as an ordinary ALU opcode.

## Build and test

`python3 tests/sh3_x64/run.py --sanitize --output <outside-source-directory>`
compiles the production CPU and executes emitted machine code against the
original interpreter. Native execution counters prevent false passes caused
by falling back for every instruction. Tests cover all supported opcode
encodings, register aliasing, flags, budget/timer/IRQ behavior, I/O observations,
live code/fetch-map changes, page boundaries, W^X failure and teardown.
Sanitizers check the C++ implementation; they do not instrument generated
machine instructions. State/RAM/observation differential tests check those.

For an experimental PS4 build, pass `CXX='clang++ -DFBNEO_SH3_X64_JIT=1'`
to the established `platform=orbis-dynamic` build. Rebuild `sh4.o` explicitly
when changing flags; make does not track arbitrary command-line flag changes.
Never copy native Linux objects into the PS4 build. A PS4 object/link success
does not prove the console has executed generated instructions.

## Performance protocol

The original runs started from reset and discarded only 180 frames. They
include Ibara's RAM test and must not be described as gameplay performance.
The user explicitly corrected this measurement on 2026-10-04.

Generate a baseline state at a visually confirmed gameplay frame. The current
local fixture is frame 3000, showing the player, enemies and explosions.
Load the exact same state for each core, with
`FBNEO_REPLAY_INPUT_FRAME_OFFSET=3000` and the same input sequence. The updated
headless harness can save gameplay images without repeatedly serializing large
states via `FBNEO_REPLAY_VIDEO_SNAPSHOTS=1`. Measure warmed gameplay separately
from setup, compare Y/JIT/JIT/Y, and verify video/audio/final-state equality.
Retain mean and tail timings; native host numbers are not PS4 frame rates.

Local evidence is under `testbuild/jit-logs`. Early prototypes were slower;
do not promote this backend merely because correctness or compilation passes.
Further work includes profitable hot-region selection, more control-transfer
instructions, and reducing validated dispatch cost. Arbitrary delayed branches,
direct block links and a complete Salvia DRC port remain unimplemented.

## Second-stage result (2026-10-04)

Branch `ps4-sh3-x64-jit-regions-20261004` extends the first-stage commit
`78b7f8ae31f28a640cad7c9da19d87de2bcf46be`, still with the Y rasterizer.
The first store/BT/BF candidate reached about 2.50 ms in one exploratory run.
Fallback counts then identified BTS/BFS as major remaining boundaries;
supporting those and pure arithmetic delay slots produced the final candidate.

Controlled gameplay Y/candidate/candidate/Y means were **2.530884 ms versus
2.127532 ms**, a **15.94% reduction in host core time**. Average per-run p95
was 3.330070 versus 2.985914 ms (10.33% lower), p99 4.636986 versus 4.324912 ms.
All four runs matched video/audio/final-state hashes. This is the same verified
post-self-test fixture, including combat and a continue screen; it is not PS4
FPS or a continuous worst-case combat result.

GCC ASan/UBSan and Clang 18 -O3 passed 44,480 non-branch opcode encodings
with three trials each, 36,864 conditional-branch boundary cases, 22,528
native/device delay-slot cases, 77 store alias/self-modification/device/remap
cases, 1,408 arithmetic edges, and existing randomized CPU/device comparisons.
Five lifecycle game/depth runs again matched Y (Ibara16/32, DDPSDOJ, DDPDFK,
Mushisam), including reset, state reload, audio-only and render-thread changes.
PS4 CPU compilation and a mixed-object link probe passed; that probe is not a
packaged core. The user subsequently requested a full PS4 build and PKG.
Evidence is in `testbuild/jit-regions-logs`; packaging evidence will be in
`testbuild/ab-jit-pkg-logs`. Native execution on the console remains untested.
The source default remains off; the experimental AB package explicitly builds
with `FBNEO_SH3_X64_JIT=1`.

## Historical first-stage result (2026-10-04)

After excluding boot/self-test, the same state and inputs produced identical
video/audio hashes and final state for Y, AA and JIT. Host means were
Y 2.53611 ms, AA 2.57765 ms,
JIT 2.96724 ms. AA was about 1.64%
slower and JIT about 17.00% slower in this sample.
The sequence includes combat and a continue screen. These are not PS4 FPS
measurements and not a demonstrated worst-case continuous-play workload.

All 37,568 supported opcode encodings (three register-state trials each),
1,408 carry/overflow/shift edge cases, 3,200 randomized CPU cases and the
existing directed lifecycle/device comparisons passed with ASan/UBSan.
Five game/depth lifecycle pairs matched Y: Ibara16/32, DDPSDOJ, DDPDFK and
Mushisam. PS4 CPU object compilation passed; native execution on the PS4
remains unverified. No new installable package is produced for this slower
prototype, and the default remains the Y interpreter.
